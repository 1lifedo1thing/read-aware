01总体判断

最难改的部分反而是对的：事件溯源、“追加事件与更新投影在同一事务”、同步的密文边界、插件 Worker 的消息协议，这些都扎实，而且有测试守着。 出问题的是它们外围的组织方式。domain 层的真正实现大多放在 features/*/lib 里；设置有三条并行的写入路径； 四个上千行的单体（阅读器视图、插件上下文、agent 回合、relay 路由）已经开始自己长出 bug。

根因只有一个：没有守门。PR 只跑一部分测试；完整的 web 测试套件现在是红的；rustfmt 和 clippy 都是红的； 没有 lint，也没有依赖边界规则；仓库里有 lint:cycles 脚本但没人跑，已经积累了 22 个循环依赖。 所以治理顺序是：先止血，再装守门，然后在守门的保护下逐块重构。不必推倒重来。

02先修：审计中找到的真实缺陷

这些不是风格问题，是现在就会出错的行为。标了“已复核”的，我读过原代码或跑过验证；其余是审计 agent 读代码得出的结论，修之前要先复现。

P0

relay：替换 blob 时先删旧数据，再检查配额

已复核

apps/relay/src/router.ts:741-751（整块上传）和 :700-706（分片上传）都是先 blobs.delete，再检查账户配额。只要配额超限就返回 413，而旧 blob 这时已经被删掉了：重新上传失败，原数据也跟着没了。另外 R2 和 D1 的记账不是原子的。

修法：先预留配额（adjust），再写入新对象，最后释放旧对象占用；失败时回滚预留。同时加一个顶层错误包装，给 5xx 响应补上 CORS 头和稳定错误码（现在任何抛错都会变成客户端看到的“网络错误”）。

P0

插件：受限授权下写全局设置，绕过了生命周期检查

已复核

不受限的 settings.commands.update/resetReading 会调用 lifecycle.assertActive（plugin-context.ts:506-513）；受限面（current/book 授权）的全局分支 :1124、:1134 直接调用 domain，没有这个检查。结果是插件在 activating/migrating 阶段也能改全局设置。

根因是受限面把每个 domain 都手抄了一遍，还用了 10 处 as typeof 断言，把穷尽性检查也关掉了。以后 domain 新增方法时，受限模式会悄悄漏掉它，类型系统不会报错。

修法：先补上检查。长期做法是给每个 domain 写一张策略表 {[K in keyof Api]: scoped | current | deny | passthrough}，用 satisfies 约束，由同一个包装器统一施加生命周期、围栏和取消信号。这样新增方法不分类就编译不过。

P0

插件资源协议：一个插件能读到另一个插件的文件

已复核

plugins.rs:533 在用户目录分支里，拿整个 plugins 根目录当包含检查的基准，而不是 <root>/<id>。于是一个插件可以 import 其他插件的模块和资源，.rollback/、.candidates/ 也能从这条路径访问到。这部分资源服务没有任何遍历测试。

修法：按插件 id 解析基准目录，拒绝以点开头的 id，补上路径遍历测试；顺便把这个文件里 16 个 Result<_, String> 换成 CommandError。

P1

旧版（v1）备份恢复直接写投影行，没有产生事件

已复核

backup-io.ts:185-192 仍然能从 UI 触发。它通过 restoreLibraryBook → library_put_book、saveAnnotation → annotation_put 直接 upsert 投影表，而这些表在 apply.rs 的 DERIVED_TABLES 里。apply.rs 头部注释写的是“apply_event 是唯一写投影的地方”，现在它依赖下次启动时的 genesis 对账来补救。这样恢复的数据在投影重建和跨设备同步时可能出问题。

修法：要么退役 v1 导入，要么改走原生的 full-backup 事件化恢复路径（选哪个需要你决定，见第 10 节）。之后把 library_put_book、annotation_put、memory_put、reading_time_import 这些原始投影写命令从 generate_handler! 里移除。

P1

会话保存分两次 IPC，不是原子的

已复核

conversation-store.ts:208-216 先 commitDomainEvents，再单独调用 ai_chat_replace，而后者会把 role、content、attachments 全部重写一遍。两次调用之间失败，展示列就会和事件不一致。与此同时，agent 的 ConversationPort.append 在产品里是空实现（conversation-port.ts:49-50）：测试和 eval 覆盖的是产品根本不走的写入路径，而 adoptLegacyThread 的“切掉最后两条”假设可能和 UI 保存发生竞态（这一点待复现）。

修法：只保留一个权威写入者。ai_chat_replace 只写 parts_json/error/seq 这些纯展示列，并和事件放进同一个原生事务；删掉端口上的 append，或者让 runtime 通过会话 domain 命令来持久化。

P1

阅读器：引擎的生命周期绑在回调的引用身份上

FoliateReaderView.tsx 里负责开书的 effect（:1966-2364）依赖 attachDocListeners，后者又依赖大约 8 个 callback。只要其中任何一个 callback 的引用变了，整本书就会被拆掉重新解析。:500 的注释记录过它已经触发过一次 “maximum update depth”。另外，crossTo 在一次跨章进行中直接 return，会把这期间的 goToFraction 拖动悄悄吞掉（疑似 bug）。

修法：见第 5 节。把引擎会话抽成纯 TS 对象，hook 只依赖 (book, bookId, readingMode)，事件处理函数用 React 19.2 的 useEffectEvent。

P2

零散但确定的问题

  • ai_chat_clear（chat.rs:229-245）里的 DELETE 和 UPDATE 不在同一个事务中。
  • write_export_file（lib.rs:101）会写入 webview 传来的任意路径，没有 dialog scope 校验。
  • diagnostics_read_logs 把 read_dir 的错误转成空列表，违反了“读取失败要显示错误，不能显示空结果”的规则。
  • 单一的全局 Mutex<Connection> 没有做中毒恢复：锁内任何 panic（例如 library_put_book 在持锁时解码封面）之后，所有存储命令都会失败，直到重启。

  • roaming 偏好先写 KV，再 fire-and-forget 提交 preference.changed 事件（roaming-preferences.ts:187-201）；事件提交失败只记日志。

04结构问题 ①：web 分层倒挂

CLAUDE.md 描述的分层是 platform → domain → features。实际情况是：domain 大多只是一层门面，真实实现放在 features/*/lib 里。例如 domain/library.ts 包装了 features/library/lib 下的 10 个模块。于是下层反过来依赖上层：

方向值导入数主要去向
domain → features139library-db、reader-settings、plugin-store、conversation-store、ai-config、各类 settings store
services → features25plugins 的网络内部、library、update
state → features13settings 的读写函数
platform → features6shutdown-owners 直接引用 plugin-host 和 reading-trace
feature ↔ feature≈300settings→plugins 67，reader→plugins 48，reader→settings 35，library↔reader、library↔shelf 双向

这种倒挂带来的具体问题

  • 设置有三条并行写入路径。UI 面板通过 state/ui.ts 的可写 atom 直接写 localKV，不经过目录校验（已复核：state/ui.ts:144-151 → app-settings.ts:50）。Agent、插件和快捷键走的是经过校验的 settings.commands.update。update-channel、annotation-prefs、menu-config 则各自直接写。更糟的是，settings domain 反过来通过 getDefaultStore() 读 UI 的 Jotai atom 来构造快照。key 到 store 的映射在三个地方手工维护。
  • 写入口不统一。阅读器创建高亮和笔记时直接调用 annotation-db（useReaderTextActions.ts:21、useReaderNoteEditor.ts:3），跳过了 domain/annotations.ts 里的样式校验和来源准备。底层仍然走 commit_events，事件契约没有破，但 agent/插件和 UI 用的是两套校验。annotation-db 和 conversation-store 还各自手写了一份“mint 事件 + invoke commit_events + 广播”，没有复用 commitDomainEvents。
  • 循环依赖靠懒加载掩盖。例如 domain/conversation-control → features/ai/agent/agent-runtime → ports → domain/book-graph-tasks → domain/index。
  • 共享引擎代码放在 reader feature 里。library 引用 reader/lib/foliate-engine 14 次，domain 引用 parse-book、reading-stats；而阅读器的排版和 CSS（settings/lib/reader-css.ts，650 行）反而放在 settings 下面。
  • 插件贡献注册表放在 Jotai atom 里（plugin-store.ts），agent 和 settings domain 都要读它。这是 settings→plugins、reader→plugins 大量耦合的主要来源。
  • 三种响应式范式并存：Jotai、手写的 subscribe/snapshot store（17 处 useSyncExternalStore）、domain 的 observe*。23 个文件在 React 之外调用 getDefaultStore()。
  • platform/ipc 只负责错误归一化，不是真正的网关：41 个 feature 文件直接用字符串命令名 invoke，deep-link onOpenUrl 在三处分别订阅。

目标分层

app/          组合根：main、App、启动序列（从 local-store 移出）、shutdown owners、availability 装配
features/*    UI + hooks → 只依赖 domain 公共 API、host、extensions、state、@read-aware/ui
host/         （原 services/）给 UI / Agent / Worker 共用的宿主能力 → domain、infra
extensions/   框架无关的贡献注册表（从 plugin-store 抽出），插件只是其中一个生产者
state/        Jotai 适配层：对 domain / extensions 可观察对象的只读镜像
domain/<ctx>/{index, commands, queries, repo, types}  → 只依赖 infra、core；不依赖 jotai、features
infra/        （原 platform/）ipc、事件存储、kv、secrets、blob、sync、OS 壳 → 只依赖 core

可以强制执行的规则：只有 app/ 和 routes/ 可以 import features/*；feature 之间只能通过对方的 index.ts 引用；invoke 只能出现在 infra/ 和 domain/*/repo.ts；@tauri-apps/* 只能出现在 infra/；jotai 不能进入 domain。

目录改名不是必需的。真正起作用的是依赖规则，外加“基线只能减少”的棘轮机制，services→host、platform→infra 这类改名只是锦上添花。改名会造成大量无意义的 diff，建议放到最后，或者干脆不做。

05结构问题 ②：几个巨型单体

P1

FoliateReaderView.tsx — 2594 行

47 个 useEffect、65 个 useRef、39 个 addEventListener，另有 18 个 effect 只是把 props 抄进 ref。里面缠在一起的职责包括：引擎的创建、解析、打开和恢复；约 750 行没有测试的输入路由（滚轮、触摸、定长版式滑动、选区稳定、点击链、键盘）；两套翻页路径（章节跳转走 runtime，翻页直接调用 view.next/prev）；为 Storybook 保留在生产代码里的回退分支。

重复且已经出现漂移的代码：iframe→视口坐标映射有 3 种写法，其中一处漏乘了 frame scale；布局属性算了两遍，而且在定长版式上的行为不一致；同一组 6 个键盘动作写了两次。

拆法：lib/reader-engine-session.ts（纯 TS，负责引擎的完整生命周期）+ useReaderEngine(book, bookId, mode)；lib/reader-input-routing.ts（纯决策函数，可以单测）+ useReaderDocumentInput（每个 document 一个 AbortController）；把 frame-geometry.ts 和 reader-layout.ts 各收敛成一处；翻页统一走 runtime，stories 改用假 session。useTextUnitNavigator（919 行，27 个 ref，状态存了两份）改成 session 类 + useSyncExternalStore。

P1

plugin-context.ts — 1944 行，其中一个闭包就有约 1540 行

contextForActor（:399-1942）里混着：授权和围栏管道（4 个几乎一样的 scoped 辅助函数）、14 个贡献点的注册、约 12 个服务 facet、85 行的 if 权限链，以及每个 domain 各一份的“不受限版本 + 受限版本”。拆分工作开过头但没做完：memory、conversations、workspace 已经是独立的文件，而且有测试。

另外有 4 张手工维护的方法路径表（PLUGIN_CALL_OPTIONS 有 67 条字符串路径，测试只校验了条数），和插件文档里“新增操作不需要改 Worker 方法列表”的说法相矛盾。

拆法：先构造一次 PluginActorKit，再拆出 facets/{settings,library,reading,annotations,memory,conversations}.ts、contributions.ts、services/*.ts；可用性检查改成“操作 → {权限, 检查}”表；RPC 元数据（options 下标、取消语义、编解码）随 facet 定义一起声明，describeContext 把它下发给 Worker，4 张字符串表随之消失。主文件缩到约 150 行，只负责组合。

P2

agent：sendPermittedTurn 约 515 行；RuntimeDeps 约 45 个成员

thread.ts:457-971 在一个方法里做了游标归一、剧透分类、grounding、章节会话与 prompt 缓存、事件翻译、重试检查点、剧透修复、持久化和后续管线调度。RuntimeDeps 实际上是服务定位器：只有 11 个是具名端口，其余是匿名的内联结构类型，另有约 150 处内联 import("@read-aware/core").X；每个工具构造器都拿到整个 deps，其中约 20 个成员只被用到一两次。这部分有约 4.6k 行 runtime 测试兜底，风险可控。

拆法：按顺序抽出 TurnPolicy → ChapterSession → AgentEventTranslator → NarrativeGuard → 回合后管线。端口按 domain 分文件具名，宿主控制类能力合并成一个 HostPort，工具族用 Pick<RuntimeDeps, …> 声明自己需要的切片。

P2

relay router.ts — 一个约 940 行的闭包加一串 if

拆法：路由表 {method, path, auth, handler}，按领域分文件，统一的错误包装（CORS + 稳定错误码，客户端可以区分不同原因的 413），decodeURIComponent 要防御非法编码。

06结构问题 ③：契约没有单一来源

同一份事实在 TS、Rust、测试 fake 里各写一遍。现在它们碰巧一致，但没有任何东西保证下去。

  • 错误码：error.rs 说新增错误码要先加到 core/errors.ts，但 annotations/conflict、changes/cursor-expired、memory/forgotten-suppressed 等只作为 Rust 字面量存在；error.rs 只定义了 7 个常量，其余约 40 个散落在约 40 个本地 fn invalid() 里。另有 27 个命令还在返回 Result<_, String>，前端拿到的只是 ipc/unknown。
  • 事件名单：core/events.ts 的 43 个事件目前和 apply.rs 完全一致，但 Rust 读的是 serde_json::Value，未知类型会被静默忽略。domain 名单在 web/domain/events.ts 和 plugin-types 里各手写了一份。
  • 记忆规则写了三份：Rust 的 memory_page.rs、agent/memory/query-page.ts、测试 fixture 里的排序。初始 importance 在产品和 fixture 里取值不同（onboarding 类记忆在产品里是 0.5，eval 里是 0.35），也就是说 eval 量到的不是产品的行为。
  • plugin-types：单文件 2672 行，173 个导出类型；能力版本只写在 JSDoc 里；市场仓库的 .d.ts 镜像有几段需要手工维护，而且没有 --check 模式。
  • settings 的 key 被硬编码进 v48/v49 迁移的 SQL 触发器，和 TS 端的 key 之间没有任何关联。

做法：沿用已有的好模式（context-bundle 的 golden JSON 被 Rust 测试 include_bytes 读取）。把错误码和事件名单都放进 core，生成一份清单，由 Rust 测试逐项比对；再为 agent 端口写一套一致性测试，同时跑在内存 fake 和桌面适配器上。

07Rust 原生端

核心比体量所暗示的要好：约 19 个原生写入者都经过 commit_events_in_transaction；有一个基于 syn 的测试，强制存储命令必须是 async、在阻塞线程池上执行、不能在池外持锁；生产代码里的 unwrap 很少（book_metadata.rs 的 86 个全部在 #[cfg(test)] 里）。需要处理的是外围：

  • 绕过投影的旧命令仍然注册着（见第 2 节）；append_events 是反方向的绕过：只追加事件，不应用。
  • lib.rs（1263 行）里没有业务逻辑，只有约 20 个平台胶水命令和一张 250 项的 handler 表，胶水部分可以移到 platform/{macos,windows,android}.rs。
  • storage/ 是平铺的 150 多个文件，mod.rs 全部 pub use x::*，73 个文件 use super::*，没有内部边界。约 189 处重复写 state::<Db>(); db.0.lock()?，应该收敛成一个 with_conn(app, "op", |c| …)，中毒恢复也顺势在这一处实现。
  • schema 迁移循环里对 v33/35/36/37/38/54 调用了当前版本的 apply_event，所以回放旧迁移的结果会随着 apply 规则变化。应该把这些钩子显式声明在迁移条目上，并断言 SCHEMA_VERSION 与 MIGRATIONS 一致。
  • syn 守卫只覆盖了 storage/ 等几个目录，扩展到所有 #[tauri::command]，就能一次性消灭“主线程阻塞 IO”这一整类问题。
  • vendor 的 auto-launch 补丁在 CI 里从来没有跑过测试，tauri-plugin-autostart 用的是插入号版本，升级后补丁可能静默失效，应锁定为 =2.5.1。
  • 5 个已注册的命令前端没有任何引用（read_events_since、checkpoint_list、library_duplicate_book_groups、annotation_delete、ai_chat_clear）；rustc 已经报告了几个死函数和从未读取的字段。

08做得好、应该保留的

  • 事件溯源核心：追加事件和投影更新在同一事务，apply.rs 是共享的重建规则，还有 syn 执行守卫。
  • 插件 Worker 协议：严格的 key 白名单、字节预算、协议版本号；授权只遍历已授予上下文的自有属性。第一方插件只依赖 @read-aware/plugin-types。
  • 同步引擎：双设备、内存 relay、配额和损坏场景都有行为测试。
  • reading-session-controller.ts：干净的适配器端口，是 domain 里值得复制的范本。
  • agent 与 web 的防腐层：pi-chat-transport.ts 里 ThreadChunk → ChatStreamChunk 的映射。
  • 发布产物干净：eval、testing、spike 代码不会进入产品包。
  • UI 规范基本得到遵守：没有原始错误文案直达用户，没有手绘 SVG，没有装饰性渐变；手写的 <button> 大多是可点击的卡片或行，真正违规的只有 4–5 处（CollectionHeader 的 input、ShelfManagementMenu 应该用 ChoiceGroup 等）。
  • 依赖版本对齐：react、TS、vite、jotai 在各 workspace 之间没有版本偏移；check:docs 的 3631 个链接全部有效。
对初始度量的两处更正。我最初用 grep 统计出的“plugin-context 被 domain 引用 25 次”全部来自测试文件（它在生产代码里只被 plugin-worker-host 引用）；“full-backup 三个文件绕过 IPC 接缝”也不对，它们只 import 了 Channel，invoke 仍然走 platform/ipc。正确的修法是让 platform/ipc 重新导出 Channel。

09治理路线图

原则：每一步都是可以单独提交、单独验证的小单元；守门先于重构，因为有了棘轮，后面每一次重构的成果才不会倒退。

0止血

修真实缺陷

  • relay 配额顺序加顶层错误包装；插件受限设置补 assertActive；插件资源按 id 做包含检查并补遍历测试。
  • ai_chat_clear 加事务；write_export_file 做 scope 校验；diagnostics_read_logs 如实报错。
  • 修好 3 个单独运行也失败的测试，并找出测试文件之间的全局泄漏源。
  • 数据库锁中毒恢复加 with_conn 辅助函数（一次改动同时解决两件事）。
1守门

装上 PR 闸门和棘轮

  • 新增 ci.yml，在 PR 和 push 上跑全部 workspace 的 typecheck + test，外加 lint:cycles。
  • 单独一次提交做 cargo fmt；修掉 clippy 的 deny 报错，之后以 -D warnings 进 CI；修正 MSRV 声明。
  • 把 apps/web/tests 和 tests/runtime 纳入 tsconfig，修掉那 36 个潜在类型错误；tests/runtime 要有能直接运行的脚本。
  • 引入 dependency-cruiser，写入第 4 节的规则，把现有违规记为基线，CI 只允许基线数减少。
  • 引入 Biome 或 oxlint：先开启浮动 Promise 和空 catch 回调规则，再禁止 features 里直接写裸表单控件（保留 allow 注释作为例外出口），再加格式化和行宽限制。
  • syn 执行守卫扩展到所有 #[tauri::command]。
2契约

单一来源 + 一致性测试

  • 错误码和事件名单统一放进 core，生成清单，由 Rust 测试逐项比对；27 个 Result<_, String> 命令迁到 CommandError。
  • 为 agent 端口写一致性测试套件，同时跑在 fake 和桌面适配器上；初始 importance 等业务规则从适配器移回 agent 或 core。
  • 会话只保留一个写入者；关闭原始投影写入命令（取决于 v1 备份的决定）。
  • 给 sync-plugin-dts 增加 --check 并接入 check:capabilities。
3结构

在棘轮保护下逐块重构

  • 设置统一写入路径：一个 key 注册表，快照由 domain 持有，atom 只读，面板统一走 settings.commands.update（useShortcutPreferences 已经是这个写法）。
  • 共享类型下沉到 domain/<ctx>/types 或 core；仓储类模块（library-db、annotation-db、conversation-store 等）移到 domain/<ctx>/repo.ts；UI 统一经过 domain 命令写入。
  • 贡献注册表从 plugin-store 抽到 extensions/；foliate-engine、parse-book 等移到 src/engine/；阅读器的 CSS 和主题从 settings 移回 reader。
  • plugin-context 拆成 facet 加策略表；FoliateReaderView 拆出引擎会话和输入路由；thread.ts 分阶段抽取；relay 改成路由表。
  • agent runtime 作为端口在 app/ 注入 domain，取代现在的懒加载 import。
4清理

删减

  • 写好 knip.json（声明入口）之后，清理确认无用的导出（knip 报告了 159 个导出和 97 个类型），以及 stats-mock.ts、两个 agent probe、./spike、Rust 死代码。

  • 更正 CLAUDE.md 里关于 foliate 的描述：源码在 apps/web/foliate-js/src，public/foliate-js 是 git 忽略的构建产物。
